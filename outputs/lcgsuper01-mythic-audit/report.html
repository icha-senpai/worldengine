Logging blind spots

  • The player-wide storage API returned 12,301 records and an empty cursor page. It did not include 147 tool movements already returned by the claim-specific searches. Its cursor exhaustion is not proof of complete worldwide storage coverage.
  • Combined tool events are deduplicated by building, timestamp, action, item ID and quantity, avoiding region-local log ID ambiguity. Counts describe observed movements, not unique physical tools.
  • Acquired and Discovered have different meanings. Published server code marks acquisition during ordinary item acquisition and successful inventory movement. Recipe and item-list discovery can reveal items without acquiring them.
  • The acquired marker has no acquisition date, quantity, counterparty or location. It is evidence of a recorded acquired item definition, not a current ownership list or a complete custody ledger.
  • Published game storage logging covers building inventories with no player owner; it is not an audit of every personal bag, bank pocket, equipped slot, dropped pile or deployable movement.
  • Published game code prunes its storage-log table after roughly 14 days. Bitjita returned archived records from July, so its retained history extends beyond that live game table.
  • Direct player-trade sessions are separate from market fills. Published code cleans resolved sessions on a five-second agent cycle. No retrospective public player-to-player trade archive was identified in the inspected providers.
  • Sources are public mirrors and published server source. Their coverage and deployed versions may differ from the live game. Absence is not proof of never having handled an item.

Useful endpoints are documented in Bitjita's API documentation. The evidence file includes the request URLs, pagination checks, trade records, acquired entries and server-source references. No background tracker was created.
